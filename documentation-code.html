01. HTML Architecture & Project Structure

The website is organised into modular static HTML pages sharing a standardised layout: a header with the main navigation, a strip for choosing the visual theme, the main content and a footer. All pages load the same script, java/base.js, which contains the behaviour of the whole site.

The script is divided into three independent parts: the style-switching system, the itinerary pages (initStoryPage) and the map page (initMapPage). The last two stop immediately if the page does not contain their elements (.area-immagini scenes and the #map container), so a single file can serve every page.

02. Data Decoupling via JSON

A core architectural decision was the separation of content, metadata and cartographic data from the HTML markup into three external files. The pages keep the structure (scenes, panels, buttons, map container) and the script fills them with the data.

Easier editing

Editors can refine narrations, add metadata or change coordinates by editing the JSON files, without touching the HTML.

Two data sets, one link

The itinerary pages read dati_tour.json, while the map page reads mappa.geojson and spostamenti.json. The two sets are connected by the links to the individual scenes (historicalLink, womenLink) stored in each location.

File Content Main structure Used by
dati_tour.json Stories and metadata of every scene in the two itineraries itinerari[] (with source_file) → tappe[], each with id, story (title, environment and levels: normal, child, scholar, each with text-less, text-standard, text-more, text-didyouknow), cinematic_context, location, project Itinerary pages
mappa.geojson The film locations GeoJSON FeatureCollection with coordinates in [longitude, latitude] order. Properties: name, films, description, narratives, historicalOrder, womenOrder, historicalLink, womenLink Map page
spostamenti.json The movements between consecutive stops historicalRoutes[] and womenRoutes[], each route with fromOrder, toOrder, transport, time, distance, directions Map page

03. CSS Themes: Style Switching & Stylesheets

Rather than duplicating HTML structures across eras, the website uses a single markup and seven stylesheets. Each stylesheet reimagines the graphic identity of Rome in Two Takes, aligning aesthetic choices with historical media technologies and graphic traditions. Each theme is described in a dedicated page in the Project Process.

Persistent Style Switching System

  1. Every page links one stylesheet (by default css/base.css) and contains a .bar-style strip. The links of the strip point directly to the CSS files.
  2. When a page loads, base.js reads localStorage.getItem("userStyle") before the page is rendered. If the value is one of the seven valid stylesheets, it becomes the href of the theme link; otherwise the script restores css/base.css.
  3. When a visitor clicks a link in the strip, the script cancels the default navigation, swaps the href of the stylesheet, saves the choice in localStorage and dispatches a custom themeChanged event.
  4. The map listens to themeChanged and changes basemap, markers and route colours without reloading the page (see section 04).

04. Interactive Map

The map page uses Leaflet. initMapPage creates a map centred on Rome, then loads mappa.geojson and spostamenti.json in parallel with Promise.all. When both files are available, the script builds the markers, the two route lines and the list of stops below the map.

Narrative filters

Three buttons select Historical Journey, Women & Urban Space or All. A location is shown if its narratives list includes the selected one. Each route line joins the visible locations in the order given by historicalOrder or womenOrder; the All view draws both lines.

List of stops

For each narrative it's shown a list of of the different stop locations. Between two consecutive stops, a note reports transport, time, distance and directions taken from spostamenti.json. The All view shows independent cards, with links to the itineraries in which the place appears.

05. Itinerary Pages & Metadata

Function Effect
next_scene(), previous_scene() Move between scenes, returning to the first or last one at the ends
showStoryView(), showMetadataView(), showQRView() Show one of the three views of a scene: story, metadata or QR code
showNormal(), showChild(), showScholar() Choose the audience of the text; the text goes back to the standard version
showLess(), showMore(), showDidYouKnow() Show the shorter, the longer or the “Did you know?” text of the active audience
toggleModal(), closeOnBackground() Open a metadata overlay (closing any other) and close it by clicking the background

Every cinematic scene incorporates metadata organised in three categories: Cinematic Context, Location and Project. The script matches each box of the metadata view to the corresponding object in the JSON file (cinematic_context, location, project) and writes one list item for each key. The properties are described with standard vocabularies:

  • Schema.org is used for the cinematic context, such as movie titles, directors and shot information.
  • CIDOC CRM and Schema.org describe the architectural heritage, the coordinates and the dates.
  • Dublin Core (dcterms) records the language and the credits of the project.

06. Technical Implementations & Best Practices

These are some of the technical implementation adopted to enrich the visual presentation and the different historical styles without polluting the HTML.

Choice Where Why
::before and ::after Stylesheets of specific eras Add decorative content to the themes that need it, without extra HTML elements
@keyframes Stylesheets with animations (in style1900.css, style1990.css, style2035.css) Animations stay in CSS, so the JavaScript does not have to manage them.
.active state of buttons base.js One global click listener marks the selected button among its siblings with an onclick attribute, instead of repeating code on every button
localStorage and themeChanged base.js The chosen era persists across pages, and the map reacts to a theme change without being coupled to the switcher code
Guard clauses initStoryPage, initMapPage Each part of the script runs only on the pages that contain its elements
Fixed viewport height Layout of the itinerary pages Typical desktop and laptop viewports are between 768px and 1080px high. A height limit of 560px lets the whole content fit without disruptive scrolling

07. Media Queries

To guarantee accessibility and smooth navigation across smartphones, tablets and desktop displays, CSS @media queries are implemented systematically across all theme stylesheets. Native media queries were deliberately chosen over external frameworks such as Bootstrap to ensure maximum design flexibility and avoid rigid grid constraints or unnecessary CSS across the different historical styles.
